# bend-osdev-blowfish

Blowfish (Schneier, 1993), a 64-bit block cipher with keys of 32 to 448 bits, on cipher-core's `LcBlock64`, with cipher-core's ECB and CBC (`modes64.bend`) over it.

The directory is `blowfish` and the entry file `blowfish/blowfish.bend`; the hub name is `bend-osdev-blowfish`. It is one of the packages split from bend-osdev-legacy-ciphers@0.1.0.0, which they supersede (that version stays on the hub as it was): cipher-core (what the ciphers share, and the 64-bit modes) and one package per cipher.

Blowfish is here for compatibility (old disks and formats): its 64-bit block has a birthday bound at 2^32 blocks. None of the code here is constant-time (see Side channels).

## Specifications

Written from the public specification only; no implementation's source was read.

* **Blowfish:** B. Schneier, *Description of a New Variable-Length Key,
  64-Bit Block Cipher (Blowfish)*, Fast Software Encryption (1993): F, the
  sixteen rounds, and the key schedule from the hexadecimal digits of pi
  (computed by `gen/tables.py`, not copied). Test vectors: the set Schneier
  publishes for Blowfish (Eric Young's), including the variable-length keys.

The test vectors were checked against the model in `ref/model.py` and Python's `cryptography` before they became laws or `check.bend` lines.

## Files

| File | Holds |
|---|---|
| `blowfish.bend` | Blowfish |
| `gen/vectors.py` | the generator of the vector laws in `LAWS.bend`, their proofs in `PROOF.bend`, and `check.bend`'s `main` and expected `#|` lines, from `ref/model.py`; `python3 gen/vectors.py` rewrites them, `--check` checks they are up to date |
| `gen/tables.py` | the generator of `blowfish.bend`'s table region (the 1042 words of pi, computed by Machin's formula); the same two modes |
| `ref/` | the differential test (`run.sh`, `gen.py`, `model.py`) |

The generated regions lie between `# BEGIN GENERATED by gen/<script>.py: <name>` and `# END GENERATED: <name>` lines; everything outside them is written by hand. After changing the vector laws, run `gen/vectors.py`.

## Public interface

The key type is opaque: built by the cipher's `key` functions from the raw key, used only through the cipher's defs. Every fallible function answers `Result<&2, &2, LcError, A>` with cipher-core's `LcError`: `LcBadKeyLength{got}` for a key of a length the cipher does not take (4 to 56, or 1 to 72 with `key_any` bytes); the 64-bit modes add `LcBadIvLength` and `LcNotBlockMultiple`.

**`blowfish.bend`**

| Def / type | Meaning |
|---|---|
| `LcBlowfishKey`, `LcBlowfish.key(o)` | 4 to 56 bytes (32 to 448 bits, as the paper says); opaque |
| `LcBlowfish.key_any(o)` | 1 to 72 bytes (the key schedule takes up to 18 words; some test sets use shorter keys) |
| `LcBlowfish.encrypt(k, b)`, `LcBlowfish.decrypt(k, b)` | one `LcBlock64` |

Everything else (`bf.*`, `LcBf*` other than the key type) is internal.

## With the 64-bit modes

cipher-modes' modes are written for 128-bit blocks, so a 64-bit cipher uses
cipher-core's `modes64.bend` instead: ECB and CBC on `LcBlock64`, the cipher
as template arguments:

```
import ../cipher-core/modes64.bend as X
import ../blowfish/blowfish.bend as C

X.Lc64.cbc_encrypt(~C.LcBlowfishKey, ~C.LcBlowfish.encrypt, k, iv, m)
X.Lc64.cbc_decrypt(~C.LcBlowfishKey, ~C.LcBlowfish.decrypt, k, iv, c)
```

For padding, cipher-modes' `Pkcs7.pad(8n, m)` and `Pkcs7.unpad(8n, m)` take
an 8-byte block size. crypto's ECB, CBC, CTR, PCBC and CBC-CS3 run over the
cipher too (crypto proves the ECB, CBC and PCBC round trips over it).

## Extension points

* **Any mode over the cipher:** it is `modes64.bend`'s template arguments (cipher-core), and crypto's; a new mode takes `~K`, `~enc`, `~dec` and never looks inside the key.
* **Key sizes and options are parameters** where the specification gives a choice: any key of 32 to 448 bits (`key_any`: 8 to 576).
* **Replaceable internals:** the key type is opaque, so the cipher's representation (its round keys, its tables) can change without touching a caller. The cipher is a list of invertible steps, decryption the steps undone in reverse order; a faster implementation (bit-sliced S-boxes, combined tables, hardware instructions) can go behind the same defs, tied to these by the vectors and the differential test.

## Laws

`LAWS.bend` (3 laws).

**For every input:**

* `blowfish_round_trip`, `blowfish_round_trip_dual`: for every Blowfish key (every key size) and every 64-bit block, decryption undoes encryption and encryption undoes decryption.

**Vectors** (proved by computation): the refusal of a 3-byte key. Schneier's vectors run compiled in `check.bend` instead: Blowfish's key schedule runs 521 encryptions, past the `--verdict` kernel's evaluation budget.

How the round trips are proved: the cipher is a list of steps, each undone by its inverse whatever its round function or key is, so no proof evaluates the cipher. Here a round and the final step are each undone by XOR (cipher-core's `u32_xor_cancel`) whatever F is.

The proofs need nothing from another package beyond its public interface and laws: cipher-core's laws (above).

## Tests

* `check.bend` runs six of Schneier's vectors (keys of 8, 1, 3 and 24 bytes) both ways (encryption, then decryption back), and the cipher through cipher-core's CBC (`modes64.bend`) over 16 KB both ways.
* `ref/run.sh` compares Blowfish (keys of 4 to 56 bytes) against Python's `cryptography` (OpenSSL) and `ref/model.py`, on random keys, blocks and messages, each a block both ways and a CBC message both ways. **`ref/model.py` was written here from the specification, by the same author as this package**, and is first checked against the specification's published vectors. When `cryptography` is missing, `run.sh` compares with the model alone and says so; it exits 77 only when `python3` is missing.

## Speed

Measured on Bend 2.0.37, native builds (`bend file.bend -o prog`), WSL2, before the split (the code is unchanged):

| Run | Time | Notes |
|---|---|---|
| Blowfish (8-byte key), CBC through modes64.bend, 256 KB both ways | 1.5 s, 58 MB peak |  |

The cipher builds its lookup tables when its key is made and keeps them in the key (Bend 2.0.37 recomputes a table def at every call). Messages have no length limit beyond memory: every loop over blocks or bytes is a tail call.

## Side channels

The S-boxes are table lookups (trees walked by the bits of a secret index). None of this is constant-time, and Bend's runtime promises nothing about running time anyway. Do not use this package where timing attacks matter.

## Dependencies

`DEPS`: `bytes` (`Octets`); `cipher-core` (the error type `LcError`, the word helpers and tables the cipher is built from, and its laws in the proofs: XOR undone and the rest).
