# bend-osdev-cast5

CAST-128 (CAST5, RFC 2144), a 64-bit block cipher with keys of 40 to 128 bits, on cipher-core's `LcBlock64`, with cipher-core's ECB and CBC (`modes64.bend`) over it. It also holds the S-boxes S1 to S4 and the round functions f1, f2, f3 that CAST-256 (the cast6 package) shares.

The directory is `cast5` and the entry file `cast5/cast5.bend`; the hub name is `bend-osdev-cast5`. It is one of the packages split from bend-osdev-legacy-ciphers@0.1.0.0, which they supersede (that version stays on the hub as it was): cipher-core (what the ciphers share, and the 64-bit modes) and one package per cipher.

CAST-128 is here for compatibility (OpenPGP, old formats): its 64-bit block has a birthday bound at 2^32 blocks. None of the code here is constant-time (see Side channels).

## Specifications

Written from the public specification only; no implementation's source was read.

* **CAST-128 (CAST5):** RFC 2144, *The CAST-128 Encryption Algorithm*
  (1997): the three round function types, S1 to S8 (Appendix A, transcribed
  into `gen/tables.py`), the key schedule, and 12 rounds for keys of up to 80
  bits. Test vectors: RFC 2144, Appendix B.1 (128-, 80- and 40-bit keys).

The test vectors were checked against the model in `ref/model.py` and Python's `cryptography` before they became laws or `check.bend` lines.

## Files

| File | Holds |
|---|---|
| `cast5.bend` | CAST-128, and the S-boxes and round functions CAST-256 shares |
| `gen/vectors.py` | the generator of the vector laws in `LAWS.bend`, their proofs in `PROOF.bend`, and `check.bend`'s `main` and expected `#|` lines, from `ref/model.py`; `python3 gen/vectors.py` rewrites them, `--check` checks they are up to date |
| `gen/tables.py` | the generator of `cast5.bend`'s table region (S1 to S8, transcribed from RFC 2144, Appendix A); the same two modes |
| `ref/` | the differential test (`run.sh`, `gen.py`, `model.py`) |

The generated regions lie between `# BEGIN GENERATED by gen/<script>.py: <name>` and `# END GENERATED: <name>` lines; everything outside them is written by hand. After changing the vector laws, run `gen/vectors.py`.

## Public interface

The key type is opaque: built by the cipher's `key` functions from the raw key, used only through the cipher's defs. Every fallible function answers `Result<&2, &2, LcError, A>` with cipher-core's `LcError`: `LcBadKeyLength{got}` for a key of a length the cipher does not take (5 to 16 bytes); the 64-bit modes add `LcBadIvLength` and `LcNotBlockMultiple`.

**`cast5.bend`**

| Def / type | Meaning |
|---|---|
| `LcCast5Key`, `LcCast5.key(o)` | 5 to 16 bytes (40 to 128 bits; up to 10 bytes, 12 rounds); opaque |
| `LcCast5.encrypt(k, b)`, `LcCast5.decrypt(k, b)` | one `LcBlock64` |

**For CAST-256** (the cast6 package uses these; they are public so that it
can):

| Def / type | Meaning |
|---|---|
| `LcCastTabs{s1, s2, s3, s4}`, `cast.tables()` | the tables of S1 to S4 (open type), built once per key |
| `LcCastTy`: `LcCastF1{}`, `LcCastF2{}`, `LcCastF3{}` | which of the three round functions (open type) |
| `cast.f(ty, t, d, km, kr)` | round function f1, f2 or f3 of RFC 2144, 2.2, on the data half d with masking key km and rotation kr |

Everything else (`cast.*` other than those, `cast5.*`, `LcCast5Rk`,
`LcCastKTabs`, `LcCastHalf`) is internal.

## With the 64-bit modes

the 128-bit modes are written for 128-bit blocks, so a 64-bit cipher uses
cipher-core's `modes64.bend` instead: ECB and CBC on `LcBlock64`, the cipher
as template arguments:

```
import ../cipher-core/modes64.bend as X
import ../cast5/cast5.bend as C

X.Lc64.cbc_encrypt(~C.LcCast5Key, ~C.LcCast5.encrypt, k, iv, m)
X.Lc64.cbc_decrypt(~C.LcCast5Key, ~C.LcCast5.decrypt, k, iv, c)
```

For padding, pkcs7's `Pkcs7.pad(8n, m)` and `Pkcs7.unpad(8n, m)` take
an 8-byte block size. crypto's ECB, CBC, CTR, PCBC and CBC-CS3 run over the
cipher too (crypto proves the ECB, CBC and PCBC round trips over it).

## Extension points

* **Any mode over the cipher:** it is `modes64.bend`'s template arguments (cipher-core), and crypto's; a new mode takes `~K`, `~enc`, `~dec` and never looks inside the key.
* **Key sizes and options are parameters** where the specification gives a choice: any key of 40 to 128 bits (12 rounds up to 80).
* **Replaceable internals:** the key type is opaque, so the cipher's representation (its round keys, its tables) can change without touching a caller. The cipher is a list of invertible steps, decryption the steps undone in reverse order; a faster implementation (bit-sliced S-boxes, combined tables, hardware instructions) can go behind the same defs, tied to these by the vectors and the differential test.
* **CAST-256** reuses the S-boxes and round functions listed above (the cast6 package).

## Laws

`LAWS.bend` (4 laws).

**For every input:**

* `cast5_round_trip`, `cast5_round_trip_dual`: for every CAST-128 key (every key size) and every 64-bit block, decryption undoes encryption and encryption undoes decryption.

**Vectors** (proved by computation): RFC 2144 B.1's 128-bit vector (`cast5_rfc2144`) and the refusal of a 4-byte key. RFC 2144's 80- and 40-bit vectors run in `check.bend`.

How the round trips are proved: the cipher is a list of steps, each undone by its inverse whatever its round function or key is, so no proof evaluates the cipher. Here the rounds are cipher-core's Feistel rounds over CAST-128's f, undone whatever f is (cipher-core's `feistel_unrun_run`, `feistel_run_unrun`), and the exchange of the halves undoes itself.

The proofs need nothing from another package beyond its public interface and laws: cipher-core's laws (above).

## Tests

* `check.bend` runs RFC 2144 B.1's three vectors both ways (encryption, then decryption back), and the cipher through cipher-core's CBC (`modes64.bend`) over 16 KB both ways.
* `ref/run.sh` compares CAST-128 (every key length) against Python's `cryptography` (OpenSSL) and `ref/model.py`, on random keys, blocks and messages, each a block both ways and a CBC message both ways. `gen.py` also compares the model with `cryptography` on 1500 random keys and blocks, so that every transcribed S-box entry is reached. **`ref/model.py` was written here from the specification, by the same author as this package**, and is first checked against the specification's published vectors. When `cryptography` is missing, `run.sh` compares with the model alone and says so; it exits 77 only when `python3` is missing.

## Speed

Measured on Bend 2.0.37, native builds (`bend file.bend -o prog`), WSL2, before the split (the code is unchanged):

| Run | Time | Notes |
|---|---|---|
| CAST-128 (128-bit key), CBC through modes64.bend, 256 KB both ways | 1.4 s, 58 MB peak |  |

The cipher builds its lookup tables when its key is made and keeps them in the key (Bend 2.0.37 recomputes a table def at every call). Messages have no length limit beyond memory: every loop over blocks or bytes is a tail call.

## Side channels

The S-boxes are table lookups (trees walked by the bits of a secret index). None of this is constant-time, and Bend's runtime promises nothing about running time anyway. Do not use this package where timing attacks matter.

## Dependencies

`DEPS`: `bytes` (`Octets`); `cipher-core` (the error type `LcError`, the word helpers and tables the cipher is built from, and its laws in the proofs: XOR undone and the rest).
