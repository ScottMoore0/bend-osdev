# bend-osdev-streebog

Streebog-256 and Streebog-512 (GOST R 34.11-2012, RFC 6986), the Russian
national hash, streaming (init, update, final) and one-shot, through
md-engine's Merkle–Damgård engine, with its transformations LPS and g_N on
their own. ecrdsa's signatures take it as their default hash.

The directory is `streebog` and the entry file `streebog/streebog.bend`; the
hub name is `bend-osdev-streebog`. It is one of the packages split from
bend-osdev-hashes@0.1.0.0, which they supersede (that version stays on the
hub as it was): md-engine (the Merkle–Damgård engine and what the hashes
share) and one package per hash.

## Specifications

Written from the public specification only; no GPL source was read.

* **Streebog:** RFC 6986, V. Dolmatov and A. Degtyarev, *GOST R
  34.11-2012: Hash Function* (August 2013): sections 6 (Pi', tau, A, C_1 to
  C_12), 7 (X, S, P, L), 8 (g_N), 9 (the procedure) and 10 (examples 1 and
  2, with their intermediate values).

## Files

| File | Holds |
|---|---|
| `streebog.bend` | Streebog-256 and Streebog-512: `HsStreebog.*`, its chaining value `HsStbCv` and tables |
| `gen/spec.py` | the specification's tables (Pi', tau, A, C_1 to C_12), with their sources |
| `gen/streebog.py` | writes the eight LPS tables, LPS and the constants (the regions "tables", "consts" and "lps" of `streebog.bend`) from `spec.py`, after checking the tables against S, P and L applied one by one |
| `gen/laws.py` | writes `LAWS.bend` and `PROOF.bend` |
| `gen/check.py` | writes `check.bend` and its expected output |
| `ref/model.py`, `ref/gen.py`, `ref/run.sh` | the differential test (Tests below) |

`python3 gen/<script>.py` rewrites what a generator writes, and `--check`
checks it is up to date. The generated regions lie between `# BEGIN
GENERATED by gen/streebog.py: <name>` and `# END GENERATED: <name>`;
everything else in `streebog.bend` is written by hand.

Bend imports do not re-export: import md-engine's `md-engine.bend` beside
`streebog.bend` to name the state type.

## Public interface

| Def | Meaning |
|---|---|
| `HsStreebog.init256()`, `HsStreebog.init512()` | the state before any byte (md-engine's `HsMdState<HsStbCv>`) |
| `HsStreebog.update(s, o)` | the state after more bytes, in any pieces (either size: init chooses) |
| `HsStreebog.final256(s)`, `HsStreebog.final512(s)` | the digest of the bytes so far, 32 or 64 bytes (a state from `init256` is finished with `final256`, one from `init512` with `final512`) |
| `HsStreebog.digest256(o)`, `HsStreebog.digest512(o)` | the digest in one call |
| `HsStreebog.compress(cv, block)` | the compression function on one 64-byte block |
| `HsStreebog.lps(x)`, `HsStreebog.g(n, h, m)` | the transformations on 512-bit vectors as 64-byte strings: LPS, and g_N(h, m) |
| `HsStreebog.tables()` | the eight LPS tables |
| `HsStbCv` | the chaining value (opaque) |

The 512-bit vectors are 64-byte strings in memory order (byte i is RFC
6986's a_i; a shorter string is a number's low bytes). Digests are in memory
order, a_0 first: RFC 6986 prints its examples the other way round, most
significant byte first.

Everything else (`hs.stb.*`, `HsStbTab`, `HsStbTabs`) is internal. The
hashes, as crypto's hash interface takes them:

```
~Hs.HsMdState<HsStbCv>, ~64n, ~32n, ~HsStreebog.init256(), ~HsStreebog.update, ~HsStreebog.final256, ~HsStreebog.digest256
~Hs.HsMdState<HsStbCv>, ~64n, ~64n, ~HsStreebog.init512(), ~HsStreebog.update, ~HsStreebog.final512, ~HsStreebog.digest512
```

## Extension points

* **The tables** are part of the chaining value, built by init from
  `HsStreebog.tables()` (from RFC 6986's Pi', tau and A, by
  `gen/streebog.py`); LPS reads only them, so another representation of
  LPS replaces the tables and `hs.stb.lps` alone.
* **The compression function is replaceable** (a Streebog without its
  tables in the chaining value): the laws hold for every compression
  function (md-engine's `md_streaming`).
* **Any user of a hash:** the defs are the template arguments crypto's hash
  interface takes (HMAC, HKDF, PBKDF2 over Streebog there), and ecrdsa
  takes either size as its hash.

## Laws

`LAWS.bend` (written by `gen/laws.py`) has 13 laws.

**For every input**, with no hypothesis, for each of Streebog-512 and
Streebog-256 (`streebog512_*`, `streebog256_*`):

* `<h>_streaming`: update over `a ++ b` is update over `a`, then `b`, from
  every state (md-engine's `md_streaming` at Streebog's defs);
* `<h>_split` and `<h>_split3`: the streaming digest of any split into two
  or three pieces is the one-shot digest;
* `<h>_length` and `<h>_digest_length`: the final digest of every state, and
  the one-shot digest of every message, has 64 (or 32) bytes.

**Vectors**, by computation: LPS(0) (`streebog_lps_zero`), and the first two
compressions of RFC 6986's example 1 (`streebog_g_example1`, g_N(h, m), and
`streebog_g0_example1`, g_0(h, N), as the RFC prints them).

**Not laws, and why.** Streebog's whole digests: one compression runs within
`--verdict`'s kernel fuel and two do not, and a digest is at least three;
so RFC 6986's four digests (M1 and M2, both sizes) are checked by
`check.bend` and the ref test, and the laws take the RFC's printed
intermediate values instead. The digests' agreement with the algorithm's
definition for every message: a hash has no specification beyond its
algorithm, so the vectors and the differential test hold it.

The proofs need nothing from another package beyond its public interface and
laws: md-engine's `md_streaming`, and bytes' `octets_len_of_list` for the
lengths.

## Tests

* `check.bend` (written by `gen/check.py`): RFC 6986's four digests (M1 and
  M2, both sizes) in one call and in three pieces through init/update/final,
  and the three intermediate values above. The expected lines are the
  specification's values.
* `ref/run.sh` (54 cases with the default seed): each size on 27 message
  lengths (around every block boundary up to three blocks, and 1000 and
  4103 bytes), whole and cut into three pieces at random points, against
  `ref/model.py`, since Python has no Streebog. **The model shares an author
  with the package**: it is checked first against RFC 6986's digests and
  intermediate values, but the differential test is against that model
  alone. Its tables are `gen/spec.py`'s, so a wrong table would show in the
  specification's vectors (which agree) rather than in the differential
  test.
* The crypto package's tests run both sizes through its hash interface, and
  HMAC over them, against Python's `hmac` over this model; ecrdsa's run
  signatures over them.

## Sizes

Native builds (Bend 2.0.37, WSL2), measured before the split (the code is
unchanged): Streebog-512 of a 1 MB pseudo-random message (its building
included) takes 2.8 s and 101 MB (each 64-byte block is 25 LPS
transformations of 64 table lookups). Updates are tail calls over the bytes,
so a message has no length limit beyond memory.

## Notes on use

* None of this code is constant-time, and Bend's runtime promises nothing
  about running time.

## Dependencies

`DEPS`: `bytes` (`Octets`, and its laws in the proofs) and `md-engine` (the
engine, `HsW2` and `HsW16`, the word helpers, and its laws in the proofs).
No hub package.
