# bend-osdev-xtea

XTEA (Needham and Wheeler, 1997), TEA with a different key schedule: a 64-bit block cipher with a 128-bit key, on cipher-core's `LcBlock64`, with cipher-core's ECB and CBC (`modes64.bend`) over it. Its steps are the tea package's.

The directory is `xtea` and the entry file `xtea/xtea.bend`; the hub name is `bend-osdev-xtea`. It is one of the packages split from bend-osdev-legacy-ciphers@0.1.0.0, which they supersede (that version stays on the hub as it was): cipher-core (what the ciphers share, and the 64-bit modes) and one package per cipher.

XTEA is here for compatibility (kernel formats): its 64-bit block has a birthday bound at 2^32 blocks. None of the code here is constant-time (see Side channels).

## Specifications

Written from the public specification only; no implementation's source was read.

* **XTEA:** R. Needham, D. Wheeler, *Tea extensions* (Cambridge Computer
  Laboratory, 1997), the routine "tean". The paper gives no test vectors and
  no byte order for the words: the order is a parameter (little-endian words
  by default, as the Linux kernel's xtea takes them; big-endian with
  `key_be`), and so is the number of cycles (32 by default).

The paper publishes no test values: `check.bend`'s lines are the model's (`ref/model.py`), and the model is checked against itself (decryption against encryption) and against this package.

## Public interface

The key type is opaque: built by the cipher's `key` functions from the raw key, used only through the cipher's defs. Every fallible function answers `Result<&2, &2, LcError, A>` with cipher-core's `LcError`: `LcBadKeyLength{got}` for a key of a length the cipher does not take (16 bytes); the 64-bit modes add `LcBadIvLength` and `LcNotBlockMultiple`.

**`xtea.bend`**

| Def / type | Meaning |
|---|---|
| `LcXteaKey`, `LcXtea.key(o)`, `LcXtea.key_be(o)` | 16 bytes, words little-endian (the named default) or big-endian, 32 cycles; opaque |
| `LcXtea.key_with(le, n, o)` | the byte order and the number of cycles as parameters |
| `LcXtea.encrypt(k, b)`, `LcXtea.decrypt(k, b)` | one `LcBlock64` |

Everything else (`xtea.*`) is internal.

## With the 64-bit modes

the 128-bit modes are written for 128-bit blocks, so a 64-bit cipher uses
cipher-core's `modes64.bend` instead: ECB and CBC on `LcBlock64`, the cipher
as template arguments:

```
import ../cipher-core/modes64.bend as X
import ../xtea/xtea.bend as C

X.Lc64.cbc_encrypt(~C.LcXteaKey, ~C.LcXtea.encrypt, k, iv, m)
X.Lc64.cbc_decrypt(~C.LcXteaKey, ~C.LcXtea.decrypt, k, iv, c)
```

For padding, pkcs7's `Pkcs7.pad(8n, m)` and `Pkcs7.unpad(8n, m)` take
an 8-byte block size. crypto's ECB, CBC, CTR, PCBC and CBC-CS3 run over the
cipher too (crypto proves the ECB, CBC and PCBC round trips over it).

## Extension points

* **Any mode over the cipher:** it is `modes64.bend`'s template arguments (cipher-core), and crypto's; a new mode takes `~K`, `~enc`, `~dec` and never looks inside the key.
* **Key sizes and options are parameters** where the specification gives a choice: the words' byte order and the number of cycles are parameters (`key_with`), the paper leaving them open.
* **Replaceable internals:** the key type is opaque, so the cipher's representation (its round keys, its tables) can change without touching a caller. The cipher is a list of invertible steps, decryption the steps undone in reverse order; a faster implementation (bit-sliced S-boxes, combined tables, hardware instructions) can go behind the same defs, tied to these by the vectors and the differential test.

## Laws

`LAWS.bend` (3 laws).

**For every input:**

* `xtea_round_trip`, `xtea_round_trip_dual`: for every XTEA key (every key size, byte order and number of cycles) and every 64-bit block, decryption undoes encryption and encryption undoes decryption.

**Vectors** (proved by computation): the refusal of a 17-byte key. No specification publishes XTEA's values: `check.bend` runs the model's, and the differential test compares with the model.

How the round trips are proved: the cipher is a list of steps, each undone by its inverse whatever its round function or key is, so no proof evaluates the cipher. Here XTEA's key is a list of the tea package's steps, so its laws are the tea package's `tea_steps_round_trip` and `tea_steps_round_trip_dual` at that list.

The proofs need nothing from another package beyond its public interface and laws: cipher-core's laws (above) and the tea package's.

## Tests

* `check.bend` runs XTEA in both byte orders (the model's values: the paper publishes none) both ways (encryption, then decryption back), and the cipher through cipher-core's CBC (`modes64.bend`) over 16 KB both ways.
* `ref/run.sh` compares XTEA against `ref/model.py` alone (neither `cryptography` nor `openssl` has it), on random keys, blocks and messages, each a block both ways and a CBC message both ways. **`ref/model.py` was written here from the specification, by the same author as this package**, and is first checked against the specification's published vectors (the paper has none: the model is checked against itself, decryption against encryption). `run.sh` exits 77 when `python3` is missing.

## Side channels

XTEA's steps are additions, shifts and XORs on words (and a key word picked by a secret-dependent index), but the words are Bend values whose operations promise no timing. None of this is constant-time, and Bend's runtime promises nothing about running time anyway. Do not use this package where timing attacks matter.

## Dependencies

`DEPS`: `bytes` (`Octets`); `cipher-core` (the error type `LcError`, the word helpers and tables the cipher is built from, and its laws in the proofs: XOR undone and the rest); `tea` (the steps TEA and XTEA share, and their laws `tea_steps_round_trip` and `tea_steps_round_trip_dual`).
