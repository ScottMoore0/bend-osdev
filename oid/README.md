# bend-osdev-oid

Object identifiers: their DER form, their dotted text form, and a registry
of the names X.509 and PKCS give them. The counterpart of Linux's
lib/oid_registry, written from the ITU-T Recommendations and the RFCs that
register the identifiers; no kernel source was read.

## Specifications

* ITU-T Recommendation X.680 (02/2021), *Information technology – Abstract
  Syntax Notation One (ASN.1): Specification of basic notation*
  (https://www.itu.int/rec/T-REC-X.680-202102-I/en): clause 32 (the object
  identifier type: 32.2 its tag, [UNIVERSAL 6]; 32.3 the value notation,
  whose XML form XMLObjIdComponentList joins XMLNumberForm numbers with
  "."; 32.11's note: at least two arcs) and 12.8 ("number": one or more
  digits, the first not zero unless it is the only one).
* ITU-T Recommendation X.690 (02/2021), *ASN.1 encoding rules*
  (https://www.itu.int/rec/T-REC-X.690-202102-I/en), 8.19: the contents
  octets, read and written by bend-osdev-asn1 (`asn1/oidval.bend` cites the
  subclauses).
* The registry's sources, each entry's `source` field naming one:
  * RFC 5280, *Internet X.509 Public Key Infrastructure Certificate and
    Certificate Revocation List (CRL) Profile* (May 2008)
    (https://www.rfc-editor.org/rfc/rfc5280.txt), Appendix A.1 (the
    attribute types id-at-*, id-domainComponent, id-emailAddress; id-pe,
    id-qt, id-ad, id-kp) and A.2 (the id-ce extensions);
  * RFC 8017, *PKCS #1: RSA Cryptography Specifications Version 2.2*
    (November 2016) (https://www.rfc-editor.org/rfc/rfc8017.txt), Appendix C
    (rsaEncryption, the RSA signature algorithms, OAEP, MGF1, pSpecified,
    and the hash functions MD2, MD5, SHA-1 and SHA-2);
  * RFC 3279, *Algorithms and Identifiers for the Internet X.509 Public Key
    Infrastructure Certificate and CRL Profile* (April 2002)
    (https://www.rfc-editor.org/rfc/rfc3279.txt): id-dsa, id-dsa-with-sha1,
    dhpublicnumber, ecdsa-with-SHA1;
  * RFC 5480, *Elliptic Curve Cryptography Subject Public Key Information*
    (March 2009) (https://www.rfc-editor.org/rfc/rfc5480.txt):
    id-ecPublicKey, id-ecDH, id-ecMQV and the named curves;
  * RFC 5758, *Internet X.509 Public Key Infrastructure: Additional
    Algorithms and Identifiers for DSA and ECDSA* (January 2010)
    (https://www.rfc-editor.org/rfc/rfc5758.txt): ECDSA and DSA with SHA-2;
  * RFC 8410, *Algorithm Identifiers for Ed25519, Ed448, X25519, and X448
    for Use in the Internet X.509 Public Key Infrastructure* (August 2018)
    (https://www.rfc-editor.org/rfc/rfc8410.txt);
  * RFC 5652, *Cryptographic Message Syntax (CMS)* (September 2009)
    (https://www.rfc-editor.org/rfc/rfc5652.txt): the content types and the
    signed attributes;
  * RFC 2315, *PKCS #7: Cryptographic Message Syntax Version 1.5* (March
    1998) (https://www.rfc-editor.org/rfc/rfc2315.txt):
    signedAndEnvelopedData;
  * NIST, *Computer Security Objects Register (CSOR), Algorithm
    Registration*
    (https://csrc.nist.gov/projects/computer-security-objects-register/algorithm-registration):
    SHA-3, SHAKE, and ECDSA and RSA PKCS #1 v1.5 with SHA-3.

## What it implements

* **Oid** (`oid.bend`): an object identifier is its arcs. An Oid is
  *valid* when it has both forms here: at least two arcs, the first 0, 1 or
  2 and the second below 40 under 0 and 1 (X.690 8.19.4), every
  subidentifier below 2^42 (asn1's bound), and every arc of at most
  fourteen decimal digits. Every constructor answers only valid Oids.
* **DER** (`oid.bend`): the OBJECT IDENTIFIER element's octets, written and
  read (under DER rules) through bend-osdev-asn1.
* **Text** (`text.bend`): the arcs in decimal joined by full stops, with a
  rule for leading zeros.
* **Registry** (`registry.bend`, generated by `gen/gen_registry.py`): 127
  object identifiers (hash, signature and key algorithms, named curves,
  name attributes, certificate extensions, key purposes, CMS content types
  and attributes, policy qualifiers and access methods), each with its name
  as the registering document's ASN.1 module writes it (`id-sha256`,
  `sha256WithRSAEncryption`, `id-ce-basicConstraints`, `secp256r1`), its
  kind and its source.

| `OidEntry{name, kind, arcs, source}` and its readers, `OidKind` (`OidKindHash`, `OidKindSigAlg`, `OidKindKeyAlg`, `OidKindCurve`, `OidKindAttribute`, `OidKindExtension`, `OidKindKeyPurpose`, `OidKindContentType`, `OidKindCmsAttribute`, `OidKindOther`), `OidSource`; `.name` of each | registry entries |

## Extension points

* **The registry** is data written by a generator: an entry is one line in
  `gen/gen_registry.py` (name, kind, arcs, source); a new source or kind is
  one more name in its list. Callers that need their own names keep their
  own list of `OidEntry` and search it the same way.
* **Text rules** are a record: a new choice (for example name forms) is one
  more field.
* **The bounds** (fourteen digits, asn1's 2^42 subidentifiers) are defs
  (`oid.max_digits`, `a1.max_octets`) that grow with Bend's run-time
  numbers.

## Laws

`LAWS.bend`, proved for **every** input:

* `der_round_trip`: when `Oid.to_der(o)` answers `Done{b}`,
  `Oid.of_der(b)` answers `Done{o}`;
* `der_canonical`: when `Oid.of_der(b)` answers `Done{o}`, `Oid.to_der(o)`
  answers `Done{b}` (DER leaves no choice);
* `text_round_trip`: a valid Oid's text reads back as it, under any rules;
* `valid_of_der`, `valid_of_text`: every Oid read is valid;
* `der_text_der`: octets read as an Oid, written as text, read back and
  encoded, are the same octets;
* `text_der_text`: an Oid read from text, encoded and decoded, is the same
  Oid;
* vectors: id-at-commonName (2.5.4.3) as DER (06 03 55 04 03) and as text,
  id-ce-basicConstraints read from text, and text refused ("2.05.4",
  "1.40", "1..2").

**How they are proved.** The DER laws (`proof_der.bend`) rest on
bend-osdev-asn1's laws: an Oid's element conforms to DER, so it decodes
back (`decode_encode`), its contents read back as its arcs
(`oid_round_trip`); octets decoded under DER are the encoder's
(`der_unique`), and contents read are the ones written (`oid_canonical`);
the element decoded is shown to be [UNIVERSAL 6] by cases. The text law
(`proof_text.bend`): decimal digits read back by Horner's rule, are each
below 10, and lead with a non-zero digit for arcs above 0; each digit's
character is a digit and not a full stop (`proof_digit.bend`: a closed
computation per digit);
so the text cuts at its full stops into the arcs' texts, each reads back as
its arc, and a valid Oid's arcs pass the length check.

`LAWS_registry.bend`, the registry's contents, for every position in it
(`List.get` on `Oid.registry()`):

* `registry_size`: 127 entries;
* `names_unique`, `arcs_unique`: two entries at different positions have
  different names (`String.eq`) and different arcs (`Oid.is_eq`);
* `lookup_found`, `name_found`: each entry is found again by its Oid, with
  its name (`Oid.lookup`, `Oid.name`);
* `named_found`: each entry's name gives back its Oid (`Oid.named`).

**How they are proved.** Uniqueness is a closed computation over the
table, quadratic in its size, cut into one def per entry (the kernel's step
budget per def; `gen/gen_regproof.py` writes them): each entry's name, and
its arcs, differ from those of every entry after it. The entry is taken by
its position and fetched again for each comparison, because an entry held
in a reused parameter carries id-domainComponent's arc 19200300, which
`--verdict`'s kernel refuses (bendlang/bend#1322, a literal of about 2^24
and up). Arcs are compared last arc first (registered arcs mostly differ in
their last), and a lemma carries that comparison over to `Oid.is_eq`'s.
The rest is induction over any list of entries: in a list whose names (or
arcs) are distinct, an entry is the first with its name (or arcs), so the
lookups find it.

**Not proved: that every entry is valid** (`Oid.valid`). It is a closed
computation too, but validity computes each arc's decimal digits and its
base-128 subidentifier octets, and the kernel's natural numbers are unary:
for the arcs 10040 and up (1.2.840.10045's ECDSA, 1.2.840.113549's PKCS,
and 19200300) that division runs out of the kernel's budget, or trips the
mismatch above. It is tested: `check.bend` checks every entry (valid, its
DER read back as it, its name and arcs found again, no name or arcs twice),
and `ref/run.sh` compares the names with OpenSSL's and Python
cryptography's.

## Tests

* `check.bend`: DER of known identifiers (X.690's {2 999 3}, PKCS #1's
  sha256WithRSAEncryption, CSOR's id-sha256, RFC 5280's
  id-domainComponent, an arc of 2^32), DER refused (octets after the
  element, cut short, a subidentifier led by 80 hex, an unfinished
  subidentifier, a non-minimal length, a constructed or other tag, no
  contents), invalid arcs, text refused (leading zeros under the default
  rules, empty arcs, signs, spaces, letters, fifteen digits, a subidentifier
  past 2^42), registry lookups by name and by Oid, and the whole registry:
  127 entries, all valid, round-tripping through DER, found again by name
  and by Oid, no name or arcs twice.
* `ref/run.sh` (495 cases with the default seed), against OpenSSL 3.0.13
  and Python cryptography 41.0.7: 50 random object identifiers (arcs to
  2^41) written as text, whose DER must be OpenSSL's (`openssl asn1parse
  -genstr OID:...`) and whose OpenSSL DER must read back to the text
  (`cryptography` reads the same text to itself, for the 26 whose arcs are
  below 2^32); 247 DER inputs that `openssl asn1parse` refuses (a
  subidentifier led by 80 hex, the last subidentifier unfinished, an octet
  after the element, cut short, a length past the end, no contents), each
  refused by the package; text with leading zeros after the first arc, which
  both tools read (refused by default, OpenSSL's DER under the lenient
  rules); 14 texts both tools refuse, refused under both rules; and 174
  registry names against `cryptography`'s constants (84) and OpenSSL's
  object names (90). It exits 77 without python3, openssl or cryptography.
  Where the tools are more lenient than X.680 (OpenSSL reads "1..2",
  "1.2." and "2.5.4.3." and `cryptography` reads "+1.2"), the package
  refuses, and those texts are not in the "both refuse" set; OpenSSL
  refuses a leading zero on the first arc only.

## Limits

* Arcs are at most fourteen decimal digits and subidentifiers below 2^42
  (Bend's run-time natural numbers are below 2^48): larger object
  identifiers, such as 2.25 UUID arcs, are refused (`OidBadArcs`,
  `OidAsn1 Asn1BadOid`).
* Text is numbers only: X.680's NameForm (`{iso standard 8571}`) is not
  read; `Oid.named` reads registry names.
* Registry lookups are linear in the registry's size.

## Dependencies

`bend-osdev-bytes` (octets), `bend-osdev-asn1` (the OBJECT IDENTIFIER
element).

bend-osdev-u32, in the proofs only: its laws of `Nat` arithmetic and words'
values (`LAWS.bend`), `Nat` division (`LAWS_div.bend`) and the order of
`Nat` and words (`LAWS_order.bend`).
