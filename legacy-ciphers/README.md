# bend-osdev-legacy-ciphers

The older block and stream ciphers a kernel's crypto layer still carries:
DES, Triple DES, SM4, Camellia, Serpent, Twofish and RC4, one file per
cipher. The 128-bit block ciphers plug into
[cipher-modes](../cipher-modes/) as its template arguments; DES and 3DES
have 64-bit blocks and come with their own ECB and CBC (`modes64.bend`).

The directory is `legacy-ciphers` and the entry file
`legacy-ciphers/legacy-ciphers.bend`; the hub name is
`bend-osdev-legacy-ciphers`.

**These ciphers are here for compatibility**: to read and write data that
old formats, disks and protocols already hold. DES's 56-bit key is broken by
exhaustive search; Triple DES is deprecated (NIST SP 800-131A Rev. 2 disallows
it for encryption after 2023, and SP 800-67 Rev. 2 limits a key bundle to
2^20 blocks); **RC4 is broken and RFC 7465 forbids it in TLS**: use it only
to interoperate with what already uses it. None of the code here is
constant-time (see Side channels).

## Specifications

Written from the public specifications only; no implementation's source was
read.

* **DES:** FIPS PUB 46-3, *Data Encryption Standard* (1999): the initial
  permutation, the cipher function f (E, the S-boxes S1 to S8, P), the key
  schedule (PC-1, PC-2, the shifts), and the inverse permutation. Test
  vectors: NIST SP 800-17, *Modes of Operation Validation System* (1998),
  Table 1 (variable plaintext) and Table 2 (variable key).
* **Triple DES (TDEA):** NIST SP 800-67 Rev. 2, *Recommendation for the
  Triple Data Encryption Algorithm Block Cipher* (2017): E_K3(D_K2(E_K1(P)))
  and its inverse, keying options 1 and 2. Test vector: the worked example in
  SP 800-67 Rev. 1 (2012), Appendix B ("The qufck brown fox jump", keying
  option 1).
* **SM4:** GB/T 32907-2016, *Information security technology - SM4 block
  cipher algorithm*, through its English descriptions: the IETF draft
  draft-ribose-cfrg-sm4 and RFC 8998, section 2.1 (the S-box, FK, CK, the
  round function T and the key schedule's T'). Test vector: GB/T 32907-2016,
  Appendix A, example 1.
* **Camellia:** RFC 3713, *A Description of the Camellia Encryption
  Algorithm* (2004): the key schedule for 128-, 192- and 256-bit keys, F, FL,
  FL^-1 and SBOX1 to SBOX4. Test vectors: RFC 3713, Appendix A.
* **Serpent:** R. Anderson, E. Biham, L. Knudsen, *Serpent: A Proposal for
  the Advanced Encryption Standard* (AES submission, 1998), the bitslice
  description: the eight S-boxes, the linear transformation and the key
  schedule (keys of up to 256 bits, a shorter key padded with a 1 bit and
  zeros). The paper fixes the bit order within the four 32-bit words but
  leaves the byte order of a block to its reference code; this package uses
  the little-endian order of the NESSIE vectors and the kernel (byte 0 is the
  low byte of X0). Test vectors: the NESSIE project's Serpent vectors (set 1
  vector 0 and set 3 vector 0, 128-bit keys).
* **Twofish:** B. Schneier, J. Kelsey, D. Whiting, D. Wagner, C. Hall,
  N. Ferguson, *Twofish: A 128-Bit Block Cipher* (AES submission, 1998): q0
  and q1 from their 4-bit tables, the MDS and RS matrices, h, g, F, the key
  schedule, and the zero padding of a shorter key (section 4.3). Test vectors:
  the paper's three vectors (128-, 192- and 256-bit keys).
* **RC4:** the key-scheduling and output algorithms as RFC 6229, *Test
  Vectors for the Stream Cipher RC4* (2011), describes them, with its test
  vectors for the key 0x0102030405 at every offset it lists; RFC 4345 for
  RC4-drop[n]. RFC 7465, *Prohibiting RC4 Cipher Suites* (2015), forbids it
  in TLS.
* **ECB and CBC** (64-bit): NIST SP 800-38A, sections 6.1 and 6.2.

The test vectors were checked against the independent models in
`ref/model.py` and, where it has the cipher, Python's `cryptography`, before
they became laws or `check.bend` lines.

## Files

| File | Holds |
|---|---|
| `legacy-ciphers.bend` | the error type `LcError`, the 64-bit block `LcBlock64`, and the word helpers the ciphers share (internal) |
| `des.bend` | DES |
| `tdes.bend` | Triple DES, on des.bend |
| `sm4.bend` | SM4 |
| `camellia.bend` | Camellia-128, -192, -256 |
| `serpent.bend` | Serpent |
| `twofish.bend` | Twofish |
| `rc4.bend` | RC4, streaming |
| `modes64.bend` | ECB and CBC for any 64-bit block cipher |
| `gen/proof.py` | the generator of `PROOF.bend`'s generated regions: the lemmas proved on a word's 32 bits (rotations, byte swaps, DES's IP and IP^-1, a block's bytes), Serpent's S-box and linear-transformation lemmas, and one proof per vector law. `python3 gen/proof.py` rewrites them, `--check` checks they are up to date |
| `gen/vectors.py` | the generator of the vector laws in `LAWS.bend` and of `check.bend`'s `main` and expected `#|` lines, from `ref/model.py`; the same two modes |

The generated regions lie between `# BEGIN GENERATED by gen/<script>.py:
<name>` and `# END GENERATED: <name>` lines; everything outside them (the
rest of `PROOF.bend`: the XOR lemmas, the Feistel, Camellia, Twofish, RC4
and mode proofs, Serpent's step lemmas and laws; the rest of `LAWS.bend`;
`check.bend`'s helpers) is written by hand. After changing the vector laws,
run `gen/vectors.py`, then `gen/proof.py`.

Bend imports do not re-export, so import the files you use: a program that
needs only Camellia imports `camellia.bend` (and `legacy-ciphers.bend` for
`LcError`), and nothing else of this package.

## Public interface

Every key type is opaque: built by the cipher's `key` functions from the raw
key, used only through the cipher's defs. Every fallible function answers
`Result<&2, &2, LcError, A>`.

**`legacy-ciphers.bend`**

| Def / type | Meaning |
|---|---|
| `LcError` | `LcBadKeyLength{got}`, `LcBadIvLength{got}`, `LcNotBlockMultiple{len}` |
| `LcBlock64{hi, lo}` | a 64-bit block, two big-endian words (open type) |
| `LcBlock64.zero()`, `LcBlock64.xor(a, b)`, `LcBlock64.hex(b)` | the zero block, XOR, hex text |
| `LcBlock64.to_octets(b)`, `LcBlock64.of_octets(o) -> Maybe` | 8 bytes and back (`None` for another length) |

**The 64-bit block ciphers** (blocks are `LcBlock64`)

| Def | Meaning |
|---|---|
| `LcDesKey`, `LcDes.key(o)` | an 8-byte key (the parity bits are ignored, as FIPS 46-3 says) |
| `LcDes.encrypt(k, b)`, `LcDes.decrypt(k, b)` | one block |
| `LcTdesKey`, `LcTdes.key(o)` | 24 bytes (keying option 1) or 16 bytes (keying option 2, K3 = K1) |
| `LcTdes.key3(o)`, `LcTdes.key2(o)` | exactly option 1, exactly option 2 |
| `LcTdes.of_des(k1, k2, k3)` | the bundle of three DES keys (any keying, option 3 included) |
| `LcTdes.encrypt(k, b)`, `LcTdes.decrypt(k, b)` | one block |

**The 128-bit block ciphers** (blocks are cipher-modes' `CmBlock`)

| Def | Meaning |
|---|---|
| `LcSm4Key`, `LcSm4.key(o)` | a 16-byte key |
| `LcCamelliaKey`, `LcCamellia.key(o)` | 16, 24 or 32 bytes (Camellia-128, -192, -256 by length) |
| `LcCamellia.key128(o)`, `key192(o)`, `key256(o)` | exactly one size |
| `LcSerpentKey`, `LcSerpent.key(o)` | 0 to 32 bytes (16, 24 and 32 are the usual sizes) |
| `LcTwofishKey`, `LcTwofish.key(o)` | 16, 24 or 32 bytes |
| `LcTwofish.key_padded(o)` | 1 to 32 bytes, zero-padded to the next size as the paper says |
| `X.encrypt(k, b)`, `X.decrypt(k, b)` for `X` = `LcSm4`, `LcCamellia`, `LcSerpent`, `LcTwofish` | one block |

**`rc4.bend`**

| Def | Meaning |
|---|---|
| `LcRc4State` | the state (S, i, j); opaque |
| `LcRc4.start(key)` | the state after the key schedule, for a key of 1 to 256 bytes |
| `LcRc4.start_drop(key, n)` | the same, with the first n keystream bytes dropped (RC4-drop[n]) |
| `LcRc4.update(st, m) -> LcRc4Out` | the next piece of data, encrypted or decrypted (the same thing), and the state after it |
| `LcRc4Out{state, data}`, `LcRc4.out_state(o)`, `LcRc4.out_data(o)` | the result (open type) |
| `LcRc4.crypt(key, m)` | the data under a key, in one call |
| `LcRc4.keystream(st, n)` | the next n keystream bytes |

**`modes64.bend`** (the cipher as template arguments `~K`, `~enc`, `~dec`,
as in cipher-modes)

| Def | Meaning |
|---|---|
| `Lc64.ecb_encrypt_blocks(~K, ~enc, +k, bs)`, `Lc64.ecb_decrypt_blocks(~K, ~dec, +k, bs)` | ECB on a list of blocks |
| `Lc64.cbc_encrypt_blocks(~K, ~enc, +k, iv, bs)`, `Lc64.cbc_decrypt_blocks(~K, ~dec, +k, iv, bs)` | CBC on a list of blocks |
| `Lc64.blocks_of(o)`, `Lc64.octets_of(bs)` | bytes to whole blocks (`LcNotBlockMultiple`) and back |
| `Lc64.ecb_encrypt(~K, ~enc, +k, m)`, `Lc64.ecb_decrypt(~K, ~dec, +k, c)` | ECB on bytes (whole blocks) |
| `Lc64.cbc_encrypt(~K, ~enc, +k, iv, m)`, `Lc64.cbc_decrypt(~K, ~dec, +k, iv, c)` | CBC on bytes, an 8-byte IV (`LcBadIvLength`) |

Everything else (`lc.*`, `des.*`, `tdes.*`, `sm4.*`, `cam.*`, `sp.*`, `tf.*`,
`rc4.*`, `m64.*`, and the types `LcTab`, `LcDesHalves`, `LcDesRk`, `LcDesSp`,
`LcCamOp`, `LcCamTabs`, `LcSpBox`, `LcSpNib`, `LcSpQ`, `LcSpOp`, `LcTfOp`,
`LcTfTabs`, `LcRc4Step`, `LcRc4Run`) is internal.

## With cipher-modes

Each 128-bit cipher has exactly the shape cipher-modes' modes take (see
cipher-modes' README): a key type, and `encrypt` and `decrypt` from key and
`CmBlock` to `CmBlock`. So every mode there runs over it unchanged:

```
import ../cipher-modes/cbc.bend as CB
import ../cipher-modes/xts.bend as XT
import ../legacy-ciphers/camellia.bend as C

CB.Cbc.encrypt(~C.LcCamelliaKey, ~C.LcCamellia.encrypt, k, iv, m)
XT.Xts.decrypt(~C.LcCamelliaKey, ~C.LcCamellia.encrypt, ~C.LcCamellia.decrypt, k1, k2, i, c)
```

and likewise CCM and CMAC. cipher-modes' round-trip laws take the cipher's
inversion as a hypothesis (`~inv: @k -> @b -> {dec(k, enc(k, b)) == b}`);
this package's `sm4_round_trip`, `camellia_round_trip`, `serpent_round_trip`
and `twofish_round_trip` are exactly that statement, proved for every key and
block, so those mode laws hold for these ciphers. `check.bend` runs every
128-bit cipher through cipher-modes' CBC over 32 KB both ways, and the
differential test compares CBC with `cryptography` (SM4, Camellia) and the
models (Serpent, Twofish).

**64-bit blocks.** cipher-modes' modes are written for 128-bit blocks
(XTS's GF(2^128) multiplication, CMAC's subkeys and CCM's B_0 are 128-bit
by definition), so DES and 3DES cannot use them. `modes64.bend` has ECB and
CBC on `LcBlock64` instead, in cipher-modes' style (the cipher as template
arguments), with laws that they undo themselves for DES and 3DES on blocks and
on bytes. For padding, cipher-modes' `Pkcs7.pad(8n, m)` and
`Pkcs7.unpad(8n, m)` take an 8-byte block size. Other 64-bit modes (CFB, OFB,
CTR, CBC-MAC) can be added to `modes64.bend` the same way.

## Errors

`LcBadKeyLength{got}` for a key of a length the cipher does not take (DES: 8;
3DES: 16 or 24; SM4: 16; Camellia and Twofish: 16, 24 or 32; Serpent: up to
32; RC4: 1 to 256), `LcBadIvLength{got}` for a 64-bit mode's IV that is not 8
bytes, and `LcNotBlockMultiple{len}` for a message that is not whole 64-bit
blocks. The 128-bit modes report cipher-modes' own `CmError`.

## Streaming

* **RC4** is a stream: `start`, then `update` once per piece, carrying the
  state; the law `rc4_streaming_*` says pieces give the output of the whole.
* **The block ciphers** work a block at a time; a message arrives in pieces
  through a mode's block layer: the last ciphertext block of one call is the
  next call's IV (`Lc64.cbc_encrypt_blocks` here, `Cbc.encrypt_blocks` in
  cipher-modes).

## Extension points

* **Any mode over these ciphers:** the 128-bit ciphers are cipher-modes'
  template arguments; the 64-bit ones are `modes64.bend`'s. A new mode takes
  `~K`, `~enc`, `~dec` and never looks inside the key.
* **Key sizes are parameters** where the specification gives a choice: the key's
  length picks Camellia's and Twofish's variant (or `key128` / `key192` /
  `key256`, `key_padded` to name it), any Serpent key up to 256 bits, any RC4
  key of 1 to 256 bytes, 3DES keying option 1 or 2 (or any three DES keys with
  `LcTdes.of_des`), and RC4-drop[n] by `start_drop`.
* **Replaceable internals:** each key type is opaque, so a cipher's
  representation (its round-key list, its tables) can change without touching
  a caller. The ciphers are written as lists of invertible steps (Feistel
  rounds, whitening, FL layers, S-box layers), with decryption the steps undone
  in reverse order; a faster implementation (bit-sliced S-boxes, combined
  tables, hardware instructions) can go behind the same defs, tied to these by
  the vectors and the differential test.
* **Not here yet:** DES weak-key detection (FIPS 74's weak and semi-weak keys,
  which the kernel can refuse), XTS or other wide modes for 64-bit ciphers,
  and RC4's variants beyond drop[n].

## Laws

`LAWS.bend` (a draft, not yet reviewed by the maintainer).

**For every input:**

* `des_round_trip`, `des_round_trip_dual`: for every DES key and every block,
  decryption undoes encryption and encryption undoes decryption;
* `tdes_round_trip`, `tdes_round_trip_dual`: the same for every 3DES key bundle
  (any three DES keys), from DES's two laws;
* `sm4_round_trip`, `camellia_round_trip`, `serpent_round_trip`,
  `twofish_round_trip`, and their `_dual` forms: the same for every key (every
  key size) and every 128-bit block;
* `rc4_involution`: from any state, the cipher applied twice gives the data
  back, for all data;
* `rc4_streaming_data`, `rc4_streaming_state`: RC4 over `a ++ b` is RC4 over
  `a`, then over `b` from the state after `a`;
* `block64_octets_round_trip`, `blocks64_octets_round_trip`: a block, and a
  list of blocks, read back from its bytes;
* `des_ecb_round_trip`, `des_cbc_round_trip`, `tdes_ecb_round_trip`,
  `tdes_cbc_round_trip`: the 64-bit modes undo themselves on blocks, for every
  key, IV and list of blocks;
* `des_cbc_octets_round_trip`, `tdes_cbc_octets_round_trip`,
  `des_ecb_octets_round_trip`, `tdes_ecb_octets_round_trip`: the same on bytes,
  for every message given as the bytes of a list of blocks,
  `Lc64.octets_of(bs)`, and every 8-byte IV (every whole-block message has
  that form, but no law states it).

How the round trips are proved: each cipher is a list of steps, each undone
by its inverse whatever its round function or key is, so none of these
proofs evaluates a cipher. A Feistel round (DES, SM4, Camellia, Twofish) is
undone by XOR (`a == (a xor b) xor b`, proved for every word); DES's IP and
IP^-1, the byte swaps and the 1-bit and Serpent rotations undo each other on
symbolic bits; Camellia's FL and FL^-1 undo each other; each Serpent S-box
and its inverse are checked on all 16 inputs and lifted to a whole layer, one
bit position at a time; the linear transformation is undone step by step.

**Vectors** (proved by computation): GB/T 32907-2016's example 1 (SM4), RFC
3713's Camellia-128 vector, NESSIE's zero key and block (Serpent), and the
refusals (bad key lengths for DES, 3DES, Camellia, Serpent and RC4; a message
that is not whole blocks). The other vectors run compiled in `check.bend`
(below) instead of being laws: the Twofish paper's, because one Twofish key
schedule takes more than 2.5 GB in the checker, near a check process's limit;
and SP 800-17's (DES), SP 800-67's (3DES) and RFC 6229's (RC4), because,
although the checker proves them (in seconds each), they run past the
`--verdict` kernel's evaluation budget (RC4's 256-step key schedule does; 128
steps do not), and a package whose proofs pass `--verdict` is worth more than
three vectors that `check.bend` runs anyway.

The proofs need nothing from another package beyond its public interface and
laws: bytes' `octets_to_of`, `octets_of_to`, `octets_of_list_idempotent`,
`octets_append_list`, and the bit slicing of word64's `W64.bits`.

## Tests

* `check.bend` runs every vector of the specifications above, both ways
  (encryption, then decryption back): SP 800-17 (five DES vectors), SP 800-67's
  three-block example in ECB and CBC with keying options 1 and 2, GB/T
  32907-2016 example 1, RFC 3713's three, NESSIE's two Serpent vectors, the
  Twofish paper's three, RFC 6229's eighteen offsets for its 40-bit key, RC4
  in three pieces and RC4-drop[1536]; and every 128-bit cipher through
  cipher-modes' CBC over 32 KB both ways (Serpent 4 KB), 3DES CBC over 16 KB
  both ways, and two refusals.
* `ref/run.sh` compares every cipher, both ways and in CBC, on random keys,
  blocks and messages (89 cases, each a block both ways and a CBC message both
  ways): DES, 3DES (both keying options), SM4, Camellia (all key sizes) and RC4
  (key lengths 1 to 256, data in two pieces, and drop[n]) against Python's
  `cryptography` (OpenSSL; DES as TripleDES with three equal keys; RC4 only at
  the key sizes it accepts), and every cipher against `ref/model.py`.
  **`ref/model.py` is an independent implementation written here from the
  specifications, by the same author as this package**; Serpent and Twofish
  are compared with it alone (`cryptography` has neither), and it is first
  checked against the specifications' published vectors. When `cryptography`
  is missing, `run.sh` compares with `model.py` alone and says so; it exits
  77 only when `python3` is missing.

## Speed and sizes

Measured on Bend 2.0.37, native builds (`bend file.bend -o prog`), WSL2:

| Cipher | Time per 16-byte (8-byte) block | Notes |
|---|---|---|
| DES | 49 us | IP and IP^-1 are computed on bits (for the proofs) |
| 3DES | about 160 us | three DES |
| SM4 | 12 us | |
| Camellia-128 | 13 us | |
| Twofish-128 | 130 us | key-dependent S-boxes through q0, q1 and MDS tables |
| Serpent-128 | 360 us | the S-box layers and rotations are computed on bits |
| RC4 | about 1 us per byte | |

Over larger messages (each run builds the message, encrypts it in CBC,
decrypts it back and compares; every last ciphertext block checked against
`cryptography` or `ref/model.py`):

| Run | Time | Peak RAM |
|---|---|---|
| SM4, CBC through cipher-modes, 1 MB both ways | 5.6 s | 225 MB |
| Camellia-128, the same | 5.5 s | 226 MB |
| Twofish-128, the same | 20.1 s | 226 MB |
| Serpent-128, the same over 256 KB | 14.4 s | 58 MB |
| 3DES, CBC through modes64.bend, 1 MB both ways | 43.3 s | 224 MB |
| RC4, 1 MB of keystream | 1.0 s | 100 MB |

`check.bend` takes about 2 s; `ref/run.sh` (89 cases) about a minute, most
of it building the case file.

Each cipher builds its lookup tables when its key is made and keeps them in
the key (Bend 2.0.37 recomputes a table def at every call, which made the
first version of DES 13 times slower, and Twofish 150 times).
Messages have no length limit beyond memory: every loop over blocks or bytes
is a tail call (the structural forms the proofs use are proved equal to
them).

Every source of slowness is in the representation, not the algorithm: the
bit-level steps the proofs need (DES's permutations, Serpent's S-boxes) and
tree lookups instead of array indexing. A faster implementation can go behind
the same defs (Extension points).

## Notes on use

* SP 800-67 requires a 3DES bundle's three keys to differ (and keying option
  1); `LcTdes.key2` and `LcTdes.of_des` exist for reading old data, and
  nothing here checks that keys differ or are not DES weak keys.
* An RC4 state must never be reused for two messages: `update` hands back the
  next state, and the involution law is about decrypting what one state
  encrypted.
* A CBC IV must be unpredictable; ECB leaks equal blocks.

## Side channels

The S-boxes are table lookups (trees walked by the bits of a secret index),
Serpent's S-box layer branches on secret bits, and RC4's state is read and
written at secret indices. None of this is constant-time, and Bend's runtime
promises nothing about running time anyway. Do not use this package where
timing attacks matter.

## Dependencies

`DEPS`: `bytes` (Octets, and its laws in the proofs), `word64` (the bit
slicing that the bit-level steps are built from) and `cipher-modes` (its open
128-bit block `CmBlock`, so the ciphers plug into its modes; the tests use its
CBC). Only `cipher-modes.bend` is imported by the ciphers, not cipher-modes'
AES, so they do not pull in bend-collections.
