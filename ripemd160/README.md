# bend-osdev-ripemd160

RIPEMD-160 (Dobbertin, Bosselaers and Preneel, 1996), streaming (init,
update, final) and one-shot, through md-engine's Merkle–Damgård engine.

The directory is `ripemd160` and the entry file `ripemd160/ripemd160.bend`;
the hub name is `bend-osdev-ripemd160`. It is one of the packages split from
bend-osdev-hashes@0.1.0.0, which they supersede (that version stays on the
hub as it was): md-engine (the Merkle–Damgård engine and what the hashes
share) and one package per hash.

## Specifications

Written from the public specification only; no GPL source was read.

* **RIPEMD-160:** H. Dobbertin, A. Bosselaers and B. Preneel, *RIPEMD-160:
  A Strengthened Version of RIPEMD*, Fast Software Encryption 1996, LNCS
  1039, pp. 71–82 (the pseudo-code: word orders r and r', rotations s and
  s', constants K and K'), and the test values on Bosselaers' RIPEMD-160
  page (homes.esat.kuleuven.be/~bosselae/ripemd160.html).

## Files

| File | Holds |
|---|---|
| `ripemd160.bend` | RIPEMD-160: `HsRipemd160.*` |
| `gen/spec.py` | the specification's tables (the word orders r and r', rotations s and s', constants K and K' and the initial value (the paper's pseudo-code)), with their sources |
| `gen/rounds.py` | writes the unrolled compression function (the region "ripemd160" of `ripemd160.bend`) from `spec.py` |
| `gen/laws.py` | writes `LAWS.bend` and `PROOF.bend` |
| `gen/check.py` | writes `check.bend` and its expected output |
| `ref/model.py`, `ref/gen.py`, `ref/run.sh` | the differential test (Tests below) |

`python3 gen/<script>.py` rewrites what a generator writes, and `--check`
checks it is up to date. The generated region lies between `# BEGIN
GENERATED by gen/rounds.py: ripemd160` and `# END GENERATED: ripemd160`;
everything else in `ripemd160.bend` is written by hand.

Bend imports do not re-export: import md-engine's `md-engine.bend` beside
`ripemd160.bend` to name the state and chaining-value types.

## Public interface

| Def | Meaning |
|---|---|
| `HsRipemd160.init()` | the state before any byte (md-engine's `HsMdState<HsW5>`) |
| `HsRipemd160.update(s, o)` | the state after more bytes (`Octets`), in any pieces |
| `HsRipemd160.final(s)` | the digest of the bytes so far (20 bytes) |
| `HsRipemd160.digest(o)` | the digest in one call (`final(update(init(), o))`) |
| `HsRipemd160.compress(cv, block)` | the compression function on one 64-byte block (a list of bytes) |
| `HsRipemd160.iv()` | the initial chaining value |

Everything else (`hs.rmd.*`) is internal. The hash, as crypto's hash
interface takes it:

```
~Hs.HsMdState<Hs.HsW5>, ~64n, ~20n, ~HsRipemd160.init(), ~HsRipemd160.update, ~HsRipemd160.final, ~HsRipemd160.digest
```

## Extension points

* **The compression function is replaceable.** `HsRipemd160.compress` is one
  def written from the tables in `gen/spec.py`; a faster one (a different
  unrolling) can replace it, and the laws hold for every compression
  function (md-engine's `md_streaming`).
* **Any user of a hash:** the defs above are the template arguments crypto's
  hash interface takes, so HMAC, HKDF and PBKDF2 (crypto) run over
  RIPEMD-160 with no adapter.
* **The engine and its types** are md-engine's (its README, Extension
  points).

## Laws

`LAWS.bend` (written by `gen/laws.py`) has 13 laws.

**For every input**, with no hypothesis:

* `ripemd160_streaming`: update over `a ++ b` is update over `a`, then `b`,
  from every state (md-engine's `md_streaming` at RIPEMD-160's defs);
* `ripemd160_split` and `ripemd160_split3`: the streaming digest of any
  split into two or three pieces is the one-shot digest;
* `ripemd160_length`: the final digest of every state has 20 bytes
  (md-engine's `w5_le_length` at the chaining value after the padding), and
  `ripemd160_digest_length`: so has the one-shot digest of every message.

**Vectors**, by computation: the eight values of the RIPEMD-160 page (all
but the million "a"), `ripemd160_paper_1` to `_8`.

**Not laws, and why.** The digest's agreement with the algorithm's
definition for every message: a hash has no specification beyond its
algorithm, so the vectors and the differential test hold it.

The proofs need nothing from another package beyond its public interface and
laws: md-engine's `md_streaming` and `w5_le_length`.

## Tests

* `check.bend` (written by `gen/check.py`): the eight values through the
  public interface, the digest in one call and in three pieces through
  init/update/final, and a million bytes "a" (the page's ninth value). The
  expected lines are the specification's values.
* `ref/run.sh` (27 cases with the default seed): RIPEMD-160 on 27 message
  lengths (around every block boundary up to three blocks, and 1000 and 4103
  bytes), whole and cut into three pieces at random points, against Python's
  `hashlib` where OpenSSL provides RIPEMD-160 (here it does), and otherwise
  `ref/model.py` (written here, from the specification, checked against the
  page's values and against hashlib where it can be), which the last line
  then names.
* The crypto package's tests run RIPEMD-160 through its hash interface, and
  HMAC and PBKDF2 over it, against Python's `hmac` and `hashlib.pbkdf2_hmac`
  (crypto/README.md).

## Sizes

Native builds (Bend 2.0.37, WSL2), a 1 MB pseudo-random message (its
building included), measured before the split (the code is unchanged): 0.12
s and 84 MB. Updates are tail calls over the bytes, so a message has no
length limit beyond memory.

## Notes on use

* None of this code is constant-time, and Bend's runtime promises nothing
  about running time.

## Dependencies

`DEPS`: `bytes` (`Octets`) and `md-engine` (the engine, the chaining-value
types and word helpers, and its laws in the proofs). No hub package.
