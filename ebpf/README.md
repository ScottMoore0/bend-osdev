# bend-osdev-ebpf

An eBPF interpreter and a verifier, written from RFC 9669 ("BPF Instruction
Set Architecture (ISA)"). The interpreter decodes and runs programs against a
bounds-checked memory model; the verifier checks control flow, register
types, stack initialisation and static bounds before a program runs.

## Specifications

* **RFC 9669**, "BPF Instruction Set Architecture (ISA)" (D. Thaler, Ed.,
  IETF, 2024): the 64-bit and 128-bit instruction encodings, the eleven
  registers, the instruction classes (ALU, ALU64, JMP, JMP32, LD, LDX, ST,
  STX), every opcode (arithmetic including the sign-extending moves and
  signed division/modulo, byte swaps, the atomic operations, the legacy
  packet loads, helper and BPF-to-BPF calls, and exit), and the semantics of
  each (wrapping arithmetic, division and modulo by zero, shift-amount
  masking, sign and zero extension).
* The Linux kernel's **verifier documentation page**
  (`Documentation/bpf/verifier.rst`), used as documentation (a prose
  description of the checks), not as source. The control-flow rules
  (reachable instructions, no falling off the end, bounded or forbidden back
  edges) and the register/stack/bounds discipline follow that page.

No GPL source was read: not the Linux kernel's interpreter or verifier, and
not any other implementation. The package is MIT (see `LICENSE`).

**Where the documents are incomplete.** RFC 9669 leaves helper functions,
map semantics, the context layout and the exact verifier algorithm to the
platform. This package makes those parameters (a helper table, map records, a
context size, verifier options) rather than fixing a platform; the choices
are listed under "Choices" below. The byte order of stored programs and of
multi-byte memory accesses is the host's, taken as a parameter (`BpfOrder`,
reused from bend-osdev-bpf).

## Choices where the documents are silent

* **Registers at entry:** R0 and R6–R9 are undefined, R1 is a pointer to the
  context at offset 0, R10 is a read-only pointer to the top of the frame's
  512-byte stack (RFC 9669, 2.2 and 4.3.1).
* **A, X, scratch — none here;** eBPF has no classic scratch memory. The
  stack is 512 bytes per frame, uninitialised until written.
* **Division and modulo by zero:** division gives 0, modulo gives the
  dividend (RFC 9669, 4.1). Signed division truncates toward zero and signed
  modulo follows it.
* **Pointers** are a region plus an offset; pointer arithmetic keeps the
  region and moves the offset (add/sub of a scalar, and pointer − pointer).
  A pointer stored to the stack 8-byte-aligned can be reloaded whole; any
  other access to stored pointer bytes fails.
* **Byte order** of stored programs and of multi-byte accesses is a parameter
  (`BpfOrder`, from bend-osdev-bpf); the standard runs use little-endian.
* **Helpers and maps** are parameters. The standard table has the three
  array-map helpers whose ids Linux assigns (`bpf_map_lookup_elem` 1,
  `bpf_map_update_elem` 2, `bpf_map_delete_elem` 3); map-value size and entry
  count come from the `EbpfMap` records.
* **The verifier is conservative.** It tracks a scalar as a known constant or
  "unknown", and a pointer as a region with an offset interval; it rejects
  what it cannot prove safe. In particular it does not model a
  lookup-result's "or null" (so dereferencing a map lookup's result is
  rejected until a richer value domain is added), it rejects programs with
  BPF-to-BPF (local) calls (the interpreter runs them; the verifier does not
  yet analyse a callee's frame), and it checks reachability only when loops
  are disabled. These are stated limitations, not unsoundness: an accepted
  program's accepted operations are the safe ones.

## Extension points

* **The helper table is a template argument** (`~helpers` of the interpreter,
  `~sigs` of the verifier), so a platform provides its own helpers and their
  signatures with no change to the engine. `ebpf_helpers.std` /
  `ebpf_helper_sigs.std` are one such pair; `ebpf_helpers.none` is the empty
  table.
* **The memory is a parameter:** `EbpfMem.new` pairs a context, a packet and
  a list of maps with a byte order. Another context layout is another
  `EbpfMem` and another `EbpfVerifyCtx`.
* **Verification is a parameter:** `EbpfVerifyOptions` (control-flow options
  and region sizes), with `default()` and `xdp(packet_size)`; the instruction
  limit and whether loops are allowed are in `EbpfCfgOptions`.
* **The byte order and the stored-program size limit** are parameters, as in
  bend-osdev-bpf.
* **Programs can be built either way:** as `EbpfRaw` slots or as `EbpfInsn`
  values; `ebpf_decode`/`ebpf_encode` convert, with a vector that a program
  using every instruction form round-trips.
* **A faster interpreter or a richer verifier** (interval/tnum scalar
  domains, map-or-null tracking, BPF-to-BPF call analysis, bounded loops)
  can be added beside these, kept to them by laws or the differential test.
* **Reference and tail forms.** `ebpf_encode`, `ebpf_decode`,
  `ebpf_to_octets`, `ebpf_of_octets` and the checks run as tail calls over
  accumulators, so a program's length is limited by memory alone; the
  structural form of encoding (`ebpf_encode.ref`) is kept for reasoning.
* **Streaming:** none. A program and its memory are read at arbitrary
  offsets, so the whole of each is needed, as eBPF itself requires.

## Laws

`LAWS.bend` (a draft, not yet reviewed by the maintainer).

**Properties, for every input (proved):**

* `load_oob`, `store_oob`: a load or store whose byte range is out of bounds
  is an error, never a value — the central guarantee of the memory model.
  Each has a witness (`witness_load_oob`) so the hypothesis is satisfiable.
* `octets_over_limit`: a stored program with a byte at offset `max` is
  refused whatever its bytes, with `witness_octets_over` (as in
  bend-osdev-bpf).

**Vectors (the specification's semantics, proved by computation):**

* RFC 9669 arithmetic: wrapping add and sub, 32-bit zero extension,
  shift-amount masking, arithmetic shift, signed division toward zero, byte
  swap.
* `round_trip`: decoding the encoding of a program that uses every
  instruction form gives it back.
* the interpreter (a move, a stack spill and reload, division by zero) and
  the verifier (accept; and rejections for an uninitialised read, an
  out-of-bounds load, and a pointer returned at exit).

**What is not proved.** The full soundness theorem — a verified program runs
to exit or the step limit and never reaches a memory error, for every input
satisfying the stated sizes — is **not** proved. What is proved is the memory
model's bounds safety (`load_oob`, `store_oob`), on which that theorem would
rest: the interpreter's every access goes through `EbpfMem.load`/`store`,
which these laws show never return a value out of bounds. The control-flow
checker and the abstract pass are exercised by the vectors and the
differential test, not by a for-all soundness proof; a full proof would need
to relate the verifier's abstract states to the interpreter's concrete states
across the control-flow graph, which is future work.

## Tests

`check.bend` runs: a context-reading program, a map lookup and dereference, a
BPF-to-BPF call, the verifier's verdicts (a local call rejected, a
zero-size-context program rejected under the default options and accepted
under `xdp`), and a stored-bytes round trip.

`ref/run.sh` runs `ref/gen.py` (seed 2026), which generates 240 random
straight-line and forward-branching register programs (ALU/ALU64, moves, sign
extension, byte swaps, conditional and unconditional jumps, exit) and compares
R0 from this interpreter against an **independent Python interpreter written
here from RFC 9669**. The two share an author, so this is a cross-check of one
reading of the specification against another, not an independent oracle.

`clang`'s BPF target was **not available** in this environment:
`clang -target bpf` reported "No available targets are compatible with triple
bpf", both for the clang behind `$HOME/bend-audit/cc-wrap` (LLVM 22, built
without the BPF backend) and for the system clang; and the WSL2 kernel has
unprivileged BPF disabled (`kernel.unprivileged_bpf_disabled = 2`), so
`BPF_PROG_TEST_RUN` could not be used either. So neither clang-compiled
objects nor the running kernel could serve as a reference, and the
independent Python model stands in. If CI has a clang with the BPF target and
a kernel that allows unprivileged `BPF_PROG_TEST_RUN`, those can be added as
further references; `run.sh` exits 77 when its one requirement (`python3`) is
missing. **CI needs no extra apt packages** beyond `python3`.
